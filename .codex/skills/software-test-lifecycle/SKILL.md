# ソフトウェアテスト・ライフサイクル

## 目的

要件、設計、実装、運用を根拠に、テストの計画から完了判定までを一貫して支援する。
推測で仕様や合否を確定せず、事実、仮定、未確認、未実施、未実装を明確に分離する。

## 適用成果物

次のうち、依頼された成果物だけを作成・更新・レビューする。複数成果物を作る場合はIDを共通化する。

1. テスト計画書
2. 単体テスト仕様書・結果書
3. 結合テスト仕様書・結果書
4. 総合テスト仕様書・結果書
5. システムテスト仕様書・結果書
6. シナリオテスト仕様書・結果書
7. 受入テスト仕様書・結果書
8. テスト結果報告書
9. 不具合管理表
10. 性能テスト計画書・結果報告書
11. 要件トレーサビリティ表

## 最優先規則

1. `AGENTS.md`、ユーザー指示、プロジェクト固有スキル、基準資料を先に読む。
2. 要件、設計、コード、既存テスト、実行結果の順に根拠をたどる。
3. 実行していないテストを合格と記載しない。
4. 未実装は不合格と混同せず、将来対象または対象外として分離する。
5. 期待結果を「正常に動作する」で済ませず、観測できる値、状態、表示、API、DB、ログ、通知で表す。
6. 1ケースで検証目的を詰め込みすぎず、失敗原因を切り分けられる粒度にする。
7. 本番送信、課金、削除、権限変更、個人情報利用、負荷印加は、明示的許可と安全な条件がある場合だけ行う。
8. 人命、安全、医療、会計、個人情報、法令に関わる最終判定をAIだけで完了しない。
9. 秘密情報、実PIN、パスワード、トークン、実在利用者データを成果物や証跡へ残さない。
10. 既存文書の書式、採番、用語、列構成がある場合は、合理的な理由なく変更しない。

## 標準ワークフロー

### 1. 指示とリポジトリを調査する

次を探索し、参照できたものと不足しているものを記録する。

- `AGENTS.md`、`.codex/skills/**/SKILL.md`、IDE固有指示
- README、要件定義書、基本設計書、詳細設計書、画面・API・DB設計書
- ソース、ルーティング、モデル、マイグレーション、設定、環境変数例
- 既存テスト、テストデータ、モック、CI、カバレッジ、静的解析
- Issue、障害票、変更履歴、リリースノート
- デプロイ、監視、バックアップ、障害復旧、運用手順
- 利用者マニュアル、業務フロー、受入条件、SLA・SLO

ユーザー指定資料を基準版とする。資料間に矛盾があれば勝手に統合せず、矛盾事項、各根拠、影響、確認先を一覧化する。

### 2. テスト基礎情報を確定する

| 項目 | 必須内容 |
|---|---|
| 目的 | 何を検証し、誰が何を判断するか |
| 対象 | 機能、画面、API、バッチ、帳票、外部連携 |
| 対象外 | 今回実施しない内容と理由 |
| 基準版 | 文書版、ブランチ、コミット、ビルド、リリース |
| 環境 | OS、端末、ブラウザ、サーバー、DB、外部サービス |
| 役割 | 実施者、確認者、承認者、利用者ロール |
| データ | 初期データ、生成方法、匿名化、リセット方法 |
| 制約 | 未実装、実機不足、接続不可、時間、権限 |
| 開始条件 | テストを開始できる条件 |
| 終了条件 | 合否・出荷・受入を判断する条件 |

基準版が取得できない場合は、確認日時と参照ファイルを代替基準として明記する。

### 3. 実装状態を分類する

- 実装済み: 実装と実行経路を確認できる
- 一部実装: UI、API、モック、土台など一部だけ存在する
- 未実装: 要件はあるが実装を確認できない
- 対象外: 今回のリリースまたは試験範囲に含めない
- 判定不能: 根拠が不足している

### 4. 要件・リスク・テストを結び付ける

要件IDがあれば維持し、なければ `REQ-001` 形式で仮採番する。

| 要件ID | 要件・業務ルール | 根拠 | 重要度 | 実装状態 | 対応ケース |
|---|---|---|---|---|---|
| REQ-001 | `<内容>` | `<ファイル・節・コード>` | 高/中/低 | `<状態>` | `<ID>` |

リスクは発生可能性、影響度、検出困難性で評価する。次を優先する。

- 人命、安全、健康への影響
- 認証、権限、テナント・組織間のデータ漏えい
- 金額、人数、残高、在庫、状態の不整合
- 保存済みに見えるが保存されていない状態
- 二重登録、二重送信、二重課金、競合更新
- 通信断、タイムアウト、外部障害、再送、復旧
- バックアップ不能、監査証跡欠落、容量枯渇

### 5. テストレベルを選ぶ

| レベル | 主目的 | 主な対象 | 実施主体 |
|---|---|---|---|
| 単体 | 小さな処理単位の正しさ | 関数、クラス、コンポーネント | 開発者 |
| 結合 | 境界とデータ受渡しの正しさ | モジュール、API、DB、外部連携 | 開発・テスト担当 |
| 総合・システム | システム全体が要件を満たすこと | 業務、機能、非機能、運用 | テスト担当 |
| シナリオ | 利用者業務が端から端まで完了すること | 複数画面・役割・時間・例外 | 業務・テスト担当 |
| 受入 | 利用者・発注者が利用可否を判断すること | 受入条件、運用、教育、帳票 | 利用者・発注者 |

同じ要件を複数レベルで重複確認する場合は、各レベルの検証目的を変える。

### 6. テスト技法を適用する

対象に応じて選択し、使わない技法は無理に追加しない。

- 同値分割、境界値分析、デシジョンテーブル
- 状態遷移、ユースケース、業務シナリオ
- ペアワイズ、組合せ、原因結果グラフ
- エラー推測、探索的テスト、回帰テスト
- 静的解析、コードレビュー、カバレッジ分析
- 負荷、ストレス、スパイク、耐久、容量、スケーラビリティ
- 脅威ベース、権限マトリクス、データ分離
- 障害注入、タイムアウト、再送、ロールバック、復旧

境界値は原則として `最小-1、最小、最小+1、通常、最大-1、最大、最大+1` から有効な組合せを選ぶ。

## テスト観点カタログ

### 機能・業務

- 主要業務の開始、継続、完了、取消、再開、差戻し、再実行
- 正常系、異常系、代替経路、禁止遷移、状態遷移
- 入力、計算、検索、並べ替え、保存、更新、削除、出力
- 日付、時刻、タイムゾーン、締日、月末、年度跨ぎ
- 複数利用者、複数端末、同時更新、排他、競合

### データ・DB

- 必須、型、桁数、文字種、空、NULL、前後空白、改行、絵文字
- 主キー、外部キー、一意制約、論理削除、履歴、監査列
- トランザクション、ロールバック、冪等性、再実行
- 画面、API、DB、帳票、通知間の整合性
- 移行前後の件数、合計、コード、文字化け、重複、欠損

### 認証・権限・セキュリティ

- 未認証、認証失敗、期限切れ、無効化、ログアウト
- ロール別の表示、操作、API強制、URL・ID直接指定
- 他利用者・他組織・他テナントのデータ分離
- 秘密情報の保存、表示、ログ、例外、ダウンロードへの混入防止
- 入力検証、XSS、SQLインジェクション、CSRF、ファイル偽装
- ロック、レート制限、復旧、監査ログ、時刻・操作者・結果

### 外部連携

- 正常、遅延、タイムアウト、4xx、5xx、不正形式、欠損値
- 同じイベントの再送、順序逆転、重複、部分成功
- Webhook署名、期限、リプレイ防止、資格情報失効
- 障害復旧後の再処理、重複防止、手動再送、監査記録

### 非機能・運用

- 応答時間、スループット、同時数、データ量、長時間運転
- 可用性、再起動、縮退、フェイルオーバー、障害復旧
- バックアップ、リストア、RPO、RTO、整合性検証
- ログ、監視、アラート、ディスク・メモリ・接続枯渇
- 対応OS、ブラウザ、端末、画面幅、アクセシビリティ
- インストール、設定変更、リリース、ロールバック、引継ぎ

### PWA・モバイル・オフライン

- 初回表示、インストール、更新、キャッシュ、古い版との混在
- カメラ、GPS、通知、マイクの許可、拒否、取消
- 機内モード、通信断、低速、復帰、バックグラウンド
- 画面ロック、端末再起動、容量不足、電池不足
- 保留データの同期、競合、重複防止、複数端末
- iOS Safari、ホーム画面起動、Android Chrome、文字拡大

## テストケース標準

### ID体系

- `UT-<機能>-001`: 単体
- `IT-<連携>-001`: 結合
- `ST-FUNC-001`: 総合・システム機能
- `ST-SCN-001`: シナリオ
- `ST-SEC-001`: セキュリティ・権限
- `ST-PERF-001`: 性能
- `ST-OPS-001`: 運用・復旧
- `UAT-<業務>-001`: 受入
- `BUG-001`: 不具合

既存採番があれば既存方式を優先し、一度公開したIDは並べ替えのために振り直さない。

### ケース列

| 項目 | 記載内容 |
|---|---|
| ケースID | 一意で安定したID |
| 要件ID | 対応要件。複数可 |
| テストレベル・分類 | 単体、結合、システム、性能等 |
| 優先度 | P0、P1、P2、P3 |
| 目的 | 何を証明するか |
| 前提条件 | 環境、役割、初期状態、設定 |
| テストデータ | 具体値、生成方法、再利用可否 |
| 手順 | 1操作1行の連番 |
| 期待結果 | 各手順または終了状態の観測結果 |
| 確認箇所 | 画面、API、DB、ログ、通知、ファイル |
| 後処理 | データ戻し、ログアウト、保留解除 |
| 自動化 | 自動、部分自動、手動 |
| 実施結果 | 未実施、合格、不合格、保留、対象外 |
| 実測結果 | 実際に観測した値と状態 |
| 証跡 | 画像、ログ、応答、DB照会、時刻 |
| 障害ID | 関連不具合 |
| 備考 | 仮定、制約、関連ケース |

手順と期待結果を対応させる。期待結果には必要に応じてHTTP状態、レスポンス項目、DB更新有無、画面メッセージ、ログイベントを含める。

### 優先度

| 優先度 | 基準 |
|---|---|
| P0 | 人命、安全、認証、データ分離、破壊、全体停止に直結 |
| P1 | 主要業務、重要整合性、主要外部連携 |
| P2 | 回避策がある機能、利用頻度が中程度 |
| P3 | 軽微な表示、低頻度、将来用 |

## 成果物別の必須構成

### テスト計画書

1. 背景、目的、品質目標
2. 対象、対象外、基準版
3. テストレベル、方針、技法
4. 体制、役割、連絡・承認経路
5. 環境、ツール、テストデータ
6. スケジュール、マイルストーン
7. 開始・中断・再開・終了条件
8. 不具合管理、変更管理、回帰方針
9. 証跡、構成管理、報告方法
10. リスク、制約、対策

### 単体テスト仕様書・結果書

- 対象関数・クラス・コンポーネントと責務
- 正常、例外、分岐、境界、戻り値、副作用
- モック・スタブ対象と契約
- カバレッジ目標と未到達理由
- 実行コマンド、結果、失敗、証跡

内部実装の行をなぞるだけでなく、公開契約と重要な不変条件を検証する。脆いテストを増やさない。

### 結合テスト仕様書・結果書

- 接続対象と責任境界
- リクエスト、レスポンス、DB反映、トランザクション
- 認証、権限、タイムアウト、再送、冪等性
- 外部サービスの正常、異常、部分障害、復旧
- モック範囲と実接続範囲

### 総合・システムテスト仕様書・結果書

- 機能要件、非機能要件、運用要件
- ロール、状態遷移、データ整合性、帳票、監査
- 外部連携、セキュリティ、性能、復旧、互換性
- 本番相当環境との差異と残存リスク

### シナリオテスト仕様書・結果書

各シナリオに、利用者、目的、開始状態、時間軸、主経路、代替経路、例外、終了状態を持たせる。最低限、次を含める。

1. 代表的な正常完了
2. 途中取消・差戻し・再開
3. 通信断・外部障害・復旧
4. 権限不足・不正操作
5. 同時操作・二重実行
6. 日跨ぎ・再ログイン・再起動
7. 重大リスクに対するフェイルセーフ

### 受入テスト仕様書・結果書

- 業務上の受入条件と要件ID
- 実利用者の役割別シナリオ
- 操作性、表示、帳票、教育、運用手順
- 代替運用、障害時対応、問い合わせ経路
- 受入、条件付き受入、差戻しの判定と承認者

開発内部の詳細より、利用者が業務を安全に完了できるかを優先する。

### テスト結果報告書

1. 結論とリリース・受入判定
2. 対象版、期間、環境、実施範囲
3. 計画対実績
4. ケース数と結果内訳
5. 要件・優先度・機能別の達成状況
6. 不具合の重大度別件数、未解決一覧、再試験結果
7. 性能・セキュリティ・運用試験結果
8. 未実施、保留、対象外と理由
9. 残存リスク、制限事項、推奨対応
10. 承認欄

合格率だけで品質を断定しない。P0/P1未実施、重大不具合、重要要件未網羅を先に報告する。

### 不具合管理表

| 項目 | 必須内容 |
|---|---|
| 障害ID・件名 | 一意IDと症状・条件 |
| 関連ケース・要件 | ケースID、要件ID |
| 環境・対象版 | 再現環境、コミット、ビルド |
| 前提・再現手順 | 最小で再現可能な条件と手順 |
| 期待・実際結果 | 根拠ある期待値と観測事実 |
| 重大度・優先度 | 定義に基づく値 |
| 再現率 | 例 `3/3` |
| 影響範囲 | 利用者、機能、データ、運用 |
| 証跡 | 画像、ログ、応答、時刻 |
| 原因・対応 | 確定事実と推測を分離 |
| 状態・担当・期限 | New、Open、Fixed、Retest、Closed等 |
| 修正版・再試験 | 修正コミット、再試験ケース・結果 |

重大度は `Critical / High / Medium / Low` とし、優先度とは分ける。原因未調査時に断定しない。

### 性能テスト計画書・結果報告書

- 対象処理、業務量、ピーク条件、データ量
- 応答時間、スループット、同時数、エラー率、資源使用率の目標
- 負荷モデル、ランプアップ、測定時間、ウォームアップ
- 負荷、ストレス、スパイク、耐久、容量の選択理由
- ツール、実行端末、監視項目、時刻同期
- 本番との差異、外部サービス制約、安全停止条件
- 実測の中央値、p90、p95、p99、最大、エラー率
- CPU、メモリ、DB接続、I/O、ネットワーク等のボトルネック
- 再現手順、ログ、グラフ、結論、改善案、再試験要否

平均値だけで判定せず、分位点とエラー率を示す。許可なく本番へ負荷をかけない。

## 実施・証跡・自動化

1. 基準版、環境、データを記録する。
2. P0スモークを先に実施する。
3. 実測結果と証跡を実施時に記録する。
4. 不合格時は障害票を作成し、最小再現を確認する。
5. 修正後は該当ケースと影響範囲の回帰試験を行う。
6. 後処理とデータ復元を確認する。

コマンド実行時はコマンド、対象ディレクトリ、終了コード、重要出力を残す。自動テスト結果と人による確認結果を分離する。既存フレームワークを優先し、依存関係を無断追加しない。

次は自動化を優先する。

- 単体の分岐・境界・例外
- APIの正常、異常、権限、境界、契約
- DB制約、マイグレーション、冪等性
- 主要画面のスモークと回帰
- ビルド、静的解析、既存CI

次は実機・手動確認を併用する。

- カメラ、GPS、マイク、通知許可、PWAインストール
- 読み上げ、視認性、操作の分かりやすさ
- 実運用のダブルチェック、教育、代替手順
- 動画内容、安全状態、受入の最終判断

## トレーサビリティと終了判定

| 要件ID | 要件概要 | ケースID | 実施結果 | 障害ID | 判定 |
|---|---|---|---|---|---|
| REQ-001 | `<要件>` | `<ケース>` | 未実施 | - | 未判定 |

次を不備として報告する。

- ケースのない要件、要件に結び付かないケース
- 根拠のない期待結果
- 未実施なのに合格扱いのケース
- 未解決のCritical・High不具合
- P0・P1の未実施または未網羅

終了条件例:

- 対象P0・P1を100%実施している
- Criticalが0件である
- 未解決Highについて責任者判断がある
- 主要要件のトレーサビリティが100%である
- 復旧、バックアップ、監査証跡を確認している
- 未実施、保留、対象外の理由が承認されている

数値はプロジェクト基準に置き換える。達成を確認できない条件は未達とする。

## 安全系システムの追加規則

対象が安全確認、人命、医療、介護、送迎、災害対応を含む場合は、次を必須にする。

- 危険な未完了状態では完了操作と完了APIを拒否する。
- UI非表示だけでなくサーバー側でも禁止条件を強制する。
- AI判定不能、カメラ失敗、通信断を「安全」と判定しない。
- 人の目視、ダブルチェック、法定装置、緊急手順を代替しない。
- 時刻、担当者、位置、操作、変更、再送の証跡を確認する。
- 端末故障、電池切れ、圏外時の代替運用を確認する。

「まもるバス」または `child_presence_detection` では、少なくとも次を含める。

- 乗車・降車・未降車人数と完了条件
- QR・手動操作・オフライン同期・`client_event_id` の冪等性
- 運転担当・確認者・管理者の権限、他園データ分離
- 車内確認、規定秒数動画、欠損、容量不足、再生権限
- AI未接続・判定不能時の人による確認
- LINE・メール併送、片系障害、再送、重複防止、同意撤回
- Webhook署名、期限付き一回限りトークン、PIN復旧監査
- iPhone Safari、ホーム画面PWA、GPS拒否、画面ロック
- 未実装機能を現行リリースの合否から分離

## 出力規則

ユーザー指定形式を優先する。指定がなければMarkdownで作成する。Word、Excel、CSV、PDF、テスト管理ツール形式の場合は、対応するスキルまたは既存テンプレートを併用する。

文書の先頭に次を置く。

1. 結論または判定
2. 対象版と試験範囲
3. 重大な未解決事項と残存リスク

表が大きい場合は概要と詳細を分離する。列名、ID、用語を全成果物で統一する。
