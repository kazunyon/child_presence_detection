# SVシステム設計書（Word）

## 目的

会計入力システム、業務管理システム、社内Webシステム向けに、初心者にも分かりやすい設計資料を `.docx` 形式で作成する。

短い説明、図、表を使い、システム、業務、資料の関係を目で追える構成を優先する。既存文書を更新する場合は、その文書の用語、章番号、表番号、書式を可能な限り保つ。

## 使用するスキル

`.docx` を作成、編集、表示確認するときは、現在の環境にある文書作成スキルを必ず併用し、その `SKILL.md` を先に最後まで読む。PDF化して確認する場合はPDF用スキルも使う。

## 作成手順

1. ユーザーの依頼、既存設計書、ソースコード、Issue、画面、DB定義から事実を集める。
2. 確定事項、推定事項、未決定事項、実環境での確認事項を分ける。
3. 対象成果物を次の7分類へ整理する。
   - 要件・企画定義書
   - 基本設計書
   - 詳細設計書
   - DB設計書
   - テスト
   - 運用
   - 利用者向け
4. 詳細な成果物名、内容、利用者、ChatGPTの確認範囲は [システム開発アウトプット一覧](references/system-development-deliverables.md) を読む。
5. 初心者が読む順番に章を並べ、各章を「概要 → 図または表 → 補足」の順で作る。
6. `.docx` を生成し、ページごとに表示確認する。
7. はみ出し、文字切れ、表の分断、用語不統一を直してから納品する。

## 標準的な成果物

ユーザーが指定した成果物を優先する。依頼が広い場合は、必要なものだけを次の順で選ぶ。

1. 要件・企画定義書
   - 目的、背景、対象範囲、現行課題、業務要件、機能要件、非機能要件、用語、未決事項
2. 基本設計書
   - システム構成図、開発環境構成図、画面、機能、帳票、権限、通知、エラー
3. 詳細設計書
   - プログラム処理、API、バッチ、入力チェック、ログ、環境変数、ライブラリ、実装規約
4. DB設計書
   - DB方針、ER図、テーブル、コード、初期データ、移行、バックアップ
5. テスト
   - 計画、単体、結合、総合、受入、結果、不具合、性能
6. 運用
   - ローカル／サーバー環境ガイド、GitHub運用、日常運用、リリース、障害、監視、保守、SLA
7. 利用者向け
   - 操作マニュアル、管理者マニュアル、FAQ、教育資料、リリースノート

複数工程を一冊にまとめる場合は、冒頭に「システム開発アウトプット一覧」と「要件・設計・テストの対応表」を置く。大きな表は分類ごとに分割する。

## Word文書のレイアウト規則

- 原則としてA4横向きにする。ユーザー指定または内容上の理由がある場合だけ変更する。
- 本文と表は `BIZ UDゴシック` 9ptを標準とする。利用できない場合はBIZ UD系の代替フォントを使う。
- 表紙タイトルは20～24pt、章見出しは14～16pt、節見出しは11～12ptを目安にする。
- 余白は上下左右15～20mmを目安とし、狭くしすぎない。
- ヘッダーまたはフッターに文書名、版数、更新日、ページ番号を置く。
- 表紙、改訂履歴、目次、本文の順を基本とする。短い資料では不要な前付けを省略する。
- 図と表には番号と短い題名を付け、本文から参照できるようにする。
- 図形、テキストボックス、矢印、表をページの右端や下端からはみ出させない。
- 図形内に長文を入れない。詳細は図の下の注記または別表へ移す。
- 大きな図や表は複数ページに分け、文字を極端に小さくしない。
- 未確定箇所は空欄にせず、`未決定`、`要確認`、`対象外` のいずれかを明記する。

## 初心者向けの文章規則

- 一文を短くし、一文一義にする。
- 最初に結論または目的を書き、その後に理由や手順を書く。
- 略語は初出時に正式名称と意味を書く。
- 専門用語は用語集へまとめ、同じ意味に複数の言葉を使わない。
- 操作手順は1操作1番号とし、ボタン名や画面名を実画面どおりに書く。
- 重要な注意、禁止事項、実環境確認事項を見分けられるようにする。
- 色だけで意味を区別せず、記号やラベルも併用する。

## システム構成図の作成規則

必要に応じて、利用者、Webブラウザ、フロントエンド、バックエンド、データベース、ファイル保存、帳票出力、取込ファイル、バックアップ、外部サービス、GitHub、ローカル開発環境、サーバー環境を含める。

主な処理は左から右へ配置する。

`利用者 → Webブラウザ → フロントエンド → バックエンド → データベース`

- 業務処理、外部連携、開発・運用基盤を枠またはページで分ける。
- ローカル開発環境、検証環境、本番環境を明確に分ける。
- ファイル保存、帳票、取込、バックアップは関係する処理の近くへ置く。
- GitHubは業務処理から分け、ソース管理と変更管理の基盤として表す。
- 矢印には `HTTPS`、`API`、`SQL`、`CSV取込` など接続の意味を短く付ける。
- 矢印の交差を避け、双方向矢印は本当に双方向の場合だけ使う。
- 推定した構成要素や接続は、確定事項に見せず `要確認` と明記する。
- 複雑な図は「全体構成」「処理構成」「開発・運用構成」に分割する。

## 表の作成規則

- 1行目を見出しとし、同じ種類の表では列名と列順を統一する。
- 見出し行を各ページで繰り返す。
- 行をできるだけページ途中で分割しない。
- 長文は箇条書きまたは複数行にし、1セルへ段落を詰め込まない。
- ID、名称、内容、担当、状態など、比較に必要な列だけを置く。
- 列幅は内容に応じて配分する。狭い列へ長文を入れない。
- 空欄の意味が曖昧にならないよう `なし`、`未決定`、`対象外` を使い分ける。
- 出典または確認元がある場合は、表の注記か出典列へ記載する。

成果物一覧では原則として次の列を使う。

| 列 | 用途 |
|---|---|
| 分類 | 7分類のいずれか |
| 工程 | 企画、要件定義、基本設計など |
| 成果物 | 文書または成果物の名称 |
| 内容 | 定義・確認する内容 |
| 主な利用者 | 利用者または確認者 |
| ChatGPTでできる確認 | ChatGPTが支援できる範囲 |
| 判定 | `◎`、`○`、`△`、`×` |

判定記号は次の意味で使う。

| 判定 | 意味 |
|---|---|
| ◎ | ChatGPTで、かなりの範囲を確認できる |
| ○ | ChatGPTで確認できるが、人による確認も必要 |
| △ | ChatGPTは補助のみ。実環境または専門家の確認が中心 |
| × | ChatGPTだけでは判断できない |

## ChatGPTの位置付け

ChatGPTを、最終承認者ではなく、整理とレビューを支援する担当者として扱う。

ChatGPTに、要件の抜け漏れ、設計間の整合、条件分岐、用語統一、Issue整理、Pull Requestレビュー支援、テスト観点、マニュアル表現、初心者向け説明を支援させる。

次の事項をChatGPTだけで承認または断定しない。

- 本番リリースの承認
- 実環境の動作確認
- 性能、負荷、同時接続数の保証
- セキュリティ診断
- 税務、法務、会計上の最終判断
- バックアップからの復元成功
- サーバー障害時の復旧判断

根拠を確認できない場合は、`確認済み` や `問題なし` と書かず、`要確認` とする。

## 仕様変更時の影響確認

仕様変更を受けたら、変更理由と変更前後を整理し、次を確認する。

- 企画目的、対象範囲、業務要件、業務フロー
- 機能一覧、画面一覧、画面遷移、画面設計、帳票、通知、権限
- 詳細設計、API、バッチ、入力チェック、ログ
- ER図、テーブル定義、コード、初期データ、移行
- 単体、結合、総合、受入の各テストケース
- 操作、管理、運用、障害、リリースの各手順
- GitHub Issue、Pull Request、リリースノート

入力項目追加、承認フロー変更、権限変更、帳票追加、CSV取込追加、外部API変更は影響範囲が広いものとして扱う。

影響確認表では、`変更対象`、`影響先`、`必要な修正`、`担当`、`状態`、`確認方法` を記録する。設計書だけを更新して、テストや運用手順を更新し忘れない。

## 完成前の確認

- 用紙方向、用紙サイズ、余白、フォント、文字サイズが指定どおりか。
- 表紙、改訂履歴、目次、見出し、図、表の順序が自然か。
- 図と表がページ内に収まり、文字や罫線が切れていないか。
- 表の見出しが次ページでも表示され、行が不自然に分断されていないか。
- 章番号、図表番号、画面ID、機能ID、テーブル名、API名が整合しているか。
- 確定、推定、未決定、実環境確認が区別されているか。
- ChatGPTの判定範囲を超えて断定していないか。
- 初心者が前提知識なしで目的、全体像、次の操作を理解できるか。
- 生成した全ページを画像またはPDFとして目視確認したか。

## 禁止する出力方法

- 大きな図や表を無理に1ページへ押し込まない。
- 極端に小さい文字を使わない。
- 図形内に長文を詰め込まない。
- 右端、下端、余白の外へ内容をはみ出させない。
- 文字切れ、行切れ、重なりを残さない。
- 根拠のない仕様、画面、API、DB項目を確定事項として作らない。
- 実環境や専門家の確認が必要な項目をChatGPTだけで `OK` または `確認済み` にしない。
- パスワード、APIキー、個人情報などの秘密情報を設計書へ平文で記載しない。
- ユーザーの指定がない限り、MarkdownやPDFだけを最終成果物として代用しない。
